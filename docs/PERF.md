# ผลวัดประสิทธิภาพ (ข้อ 29)

วัดด้วย Playwright + Chrome (headless, macOS, โหมด mock, 1280×800) นับช่วงเวลาระหว่างเฟรม `requestAnimationFrame` เทียบ **ฉบับปัจจุบัน** กับ `b199cc3` (ก่อนรอบขัดเกลา) สคริปต์: `scripts/qa-flow.mjs` (ตลอด flow) และสคริปต์วัดคู่สองฉบับ (3 ช่วงที่มีในทั้งสองฉบับ ทำ 2 รอบ)

| ช่วง | ปัจจุบัน | b199cc3 |
|---|---|---|
| หน้าแรก → สมุด (ปัจจุบันมีพลิกปก 3D 1.3 วิ) | 60 fps, ช้าสุด 17 ms, เฟรม >50ms = 0 (2 รอบ) | 60 fps, 17 ms, 0 |
| ปาดสีลากต่อเนื่อง | รอบ 1: 58 fps low1% 18 fps ช้าสุด **117 ms (1 เฟรม)** · รอบ 2: 60 fps ช้าสุด 17 ms | 60 fps ช้าสุด 17 ms (2 รอบ) |
| ลำดับบันทึก (ปัจจุบันนานกว่าเดิม 0.3 วิ เพราะพลิกปก) | 60 fps ช้าสุด 17 ms เฟรม >50ms = 0 (2 รอบ) | รอบ 1: ช้าสุด 67 ms (1 เฟรม) · รอบ 2: 33 ms |

ใน `qa-flow.mjs` (เดินทั้ง flow) ทุกช่วงได้ 60 fps ช้าสุด 17 ms: พลิกปกเปิด/ปิด, พลิกแผ่น, เปลี่ยนวัน, สาดสี, ปาดสี, ลำดับบันทึก

**ข้อสังเกต**
- เฟรมสะดุด 117 ms ครั้งเดียวในรอบแรกของการปาดสีฉบับปัจจุบัน ไม่เกิดซ้ำในรอบสอง น่าจะเป็นการคอมไพล์ shader ครั้งแรก (ฉบับเก่าก็มีเฟรมช้า 67 ms ในลำดับบันทึกรอบแรก) ไม่ถือว่าเป็นการถดถอย แต่ควรดูบน iPad จริง
- Headless Chrome ล็อกเฟรมที่ 60 ตัวเลขนี้บอกได้ว่า "ไม่มีงานหนักบน main thread" ไม่ได้บอกต้นทุน GPU บน iPad Safari
- **ยังไม่ได้วัดบน iPad จริง** ต้องวัดเองด้วยสายตา: พลิกปก 3D (perspective + clip-path) และการพลิกแผ่นบน Safari
